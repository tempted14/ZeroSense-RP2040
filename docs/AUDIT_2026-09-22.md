# Project audit before disconnect fixes — 2026-09-22

Scope: firmware host/device USB, HID parsing and scheduling, Windows serial and
configuration lifecycle, profiles/settings/UI, OCR/hotkeys, installation,
release/update tooling, CI and tests. Existing horizontal-control work and local
research documents were present before the audit and were preserved.

## Observations before source changes

- Windows enumerated the RP2350 CDC interface on COM4. ZeroSense was closed.
- Three STATUS-only samples identified downstream mouse `3554:F58C`, FIRE=OFF,
  4566 downstream reports, 4383 upstream reports, no decode/saturation/recovery
  events, current queue zero, maximum active report gap 1996 us.
- Counts were unchanged during the short sample. This is consistent with an idle
  mouse and does not prove a failure. No random disconnect was reproduced.
- Baseline: 37/37 .NET tests and 34/34 Python tests passed.
- User clarified the board stays enumerated and the mouse freezes with the
  app **closed**, during plain passthrough at a configured 1000 Hz. This rules
  out app/recoil activation as a necessary trigger. The CDC blocking defect
  below is real but does **not** explain this app-closed case by itself.

## Prioritized findings

## Limits and preserved behavior

There is no evidence that buying another adapter will fix the software paths
above. Nor does this audit exclude electrical power/signal/CC problems or an
actual mouse/PIO-USB compatibility problem at 1000 Hz. A quiet interrupt endpoint is legal: do not
reset a mouse merely because it has not moved. A genuinely wedged busy endpoint
or stopped PIO host core needs live counters and hardware reproduction.

Keep 127x limits, current profiles, horizontal options, timing variance, delta
noise, additive mouse forwarding, exact configuration validation, and explicit
re-arm after faults. No automatic reflashing or GitHub release is part of this
diagnostic change.

## Changes after the audit

- Keep mounted HID descriptors/addresses after exhausted receive submissions;
  retry at 5 ms, then 100 ms after the threshold. Fail-safe disarm and button
  release are retained; availability returns only after a decoded report.
- Queue whole CDC replies in a fixed 4096-byte buffer, draining at most 128 bytes
  per loop through TinyUSB's nonblocking API. Bound serial receive work too.
  Dropped replies are counted; protocol retries recover dropped acknowledgements.
- Ignore UI callbacks whose sender is no longer the active connection.
- Extend backward-compatible metrics and diagnostic exports. Add a firmware
  build identifier, host-task heartbeat age, receive-submission
  failures, HID unmounts and dropped CDC replies.
- Check each native restore/test exit code in CI/release PowerShell steps.

No speculative PIO driver replacement, reset-on-idle timer, automatic whole-board
reset, gain changes, or input noise/timing changes were introduced.

## Capturing the remaining app-closed freeze

Do not unplug/reset immediately when it freezes. With ZeroSense closed, run:

```powershell
.\tools\read_usb_status.ps1 -Port COM4
```

Use the actual COM port if it changed. Move the mouse during the three samples.
The script sends STATUS only; it does not arm, configure or reset the board.
Opening CDC briefly changes DTR; the script closes it again when complete.
On the diagnostic firmware, look for `BUILD:USB-RECOVERY-20260922`.

| Observation across samples | Interpretation / next check |
|---|---|
| `HOST_TASK_AGE_MS` grows continuously | Core 1 is not completing host-loop iterations. Suspect blocked host/PIO work; ordinary mouse inactivity does not cause this. |
| `HOST_TASK_AGE_MS` stays low, `HOST_REPORTS` stays fixed **while moving/clicking** | Host loop is alive but the downstream endpoint/device is not delivering callbacks; could be a wedged pending transfer, device or signal/power problem. Idle alone is not a failure. |
| `HOST_QUEUE_FAILURES` rises | TinyUSB rejects receive submission; the new bounded recovery path is being exercised. |
| `HOST_UNMOUNTS` rises | Host stack actually observed an interface removal; investigate downstream connection/power/enumeration. |
| Reports increase but `HID_SENT` stops and `HID_BUSY` rises | Upstream HID endpoint is not accepting reports. |
| `CDC_DROPPED` rises | Status/ACK output exceeded the bounded queue; physical HID is no longer blocked by that queue. |

Also record whether unplugging **only the mouse** restores movement, or a board
reset is required. These are diagnostic clues, not a confirmed root cause.
The firmware currently on the user's board has only the older counters; the
new fields require flashing the diagnostic UF2 after the user chooses to do so.

Hardware acceptance remains outstanding: sustained 1000 Hz movement with the
app closed, app-open/disarmed forwarding, rapid button/wheel/side-button tests,
mouse unplug/replug, CDC reader backpressure, and armed-output/fail-safe checks.

## New physical freeze capture

The user captured a freeze on the diagnostic RP2350 firmware at 1000 Hz with
the Windows app closed. Across three STATUS samples about one second apart:

| Counter | Samples | Meaning |
|---|---|---|
| `HOST_TASK_AGE_MS` | 61866, 62907, 63928 | Core 1's host loop had not completed an iteration for more than a minute. |
| `HOST_REPORTS` | 46016, 46016, 46016 | Mouse input callbacks stopped. |
| `HID_SENT` | 45546, 45546, 45546 | Nothing new reached the upstream HID endpoint. |
| `HOST_QUEUE_FAILURES`, `HOST_UNMOUNTS`, `HOST_DECODE_ERRORS` | all 0 | The receive retry and decoder paths were not the immediate failure. |
| `MOUSE:CONNECTED` | all 3 | The connection label was the last published state, not proof that core 1 was alive. |

This is evidence of a stopped host core or work on that core, not proof of a
specific instruction. The pinned Pico-PIO-USB v0.7.2 source contains an
unbounded TX EOP program-counter poll. An [upstream report of the same host-core
hang](https://github.com/sekigon-gonnoc/Pico-PIO-USB/issues/197) identifies
that wait, and [PR #206](https://github.com/sekigon-gonnoc/Pico-PIO-USB/pull/206)
replaces it with a fixed wait. We vendored the pinned source and applied only
that targeted change, with fractional-divider timing for this 120 MHz RP2350.
The complete upstream PR remains unmerged after compatibility reports; it was
not applied wholesale. Native timing fixtures pass. The RP2350 UF2 builds and
passes its target-family check, but a sustained test on this actual board and
mouse is still required.

Core 0 now detects when the host loop has not completed for more than 500 ms.
It releases cached physical buttons/deltas, revokes generated output, and
reports `MOUSE:HOST_ERROR` in response to STATUS instead of the stale connected
label seen in the capture. The later local build, which also adds the 2.5×
automatic-weapon boost, reports `BUILD:HOST-FIX-OPTIC-20260922`.
There is no automatic core/board restart; doing so while a PIO IRQ or DMA
transfer may be active needs separate hardware validation.

Primary implementation reference checked alongside the linked local library:
[Adafruit CDC implementation](https://github.com/adafruit/Adafruit_TinyUSB_Arduino/blob/master/src/arduino/Adafruit_USBD_CDC.cpp).
